# HireWithSense — Architecture & Production Plan

> Status: implemented (v2, October 2026). This document is the reference for the system design;
> the other documents in this folder cover setup, development, the API, deployment, AI and
> scoring, code execution, the frontend and compliance. Architecture, entity-relationship,
> database and use-case diagrams are in [DIAGRAMS.md](DIAGRAMS.md).

## 1. Product vision

HireWithSense is an AI-assisted technical interviewing platform. A recruiter configures a job
with competencies (a weighted rubric), a question bank, and coding problems. Candidates are
invited by email, upload a resume, consent to AI use, and run a timed interview in the browser:
a conversational section (an AI interviewer asks resume- and role-grounded questions; the
candidate answers by voice or text) and a coding section (an in-browser IDE with sample and
hidden test cases). The system produces an evidence-anchored report per competency. Recruiters
review reports, integrity signals and rankings, and make the hiring decision themselves; the
AI never auto-rejects.

## 2. What was wrong with the MVP (and what this rewrite fixes)

| MVP                                                             | v2                                                                                                |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Untyped JS, ad-hoc validation per route                         | TypeScript end to end, Zod contracts shared between API and web, OpenAPI generated from them      |
| Mongo documents with unbounded embedded arrays (transcript, submissions inside the interview) | PostgreSQL relational schema; append-only event tables; indexes on every access path |
| Single long-lived JWT, no logout/revocation                     | 15-minute access JWT + rotating refresh tokens (hashed, revocable sessions), lockout, audit log    |
| `user`/`admin` global roles, no tenancy                         | Organizations with memberships (owner/admin/member); candidates are global; all recruiter data is org-scoped |
| Separate "oral" vs "coding" interviews                          | One interview with ordered sections (conversation, coding) snapshotted from the job's interview plan |
| Timer enforced only by `endsAt` checks                          | Server-authoritative section/overall deadlines, background expiry sweep, grace handling            |
| Code run synchronously, serially, with provider polling in request path | Pluggable `CodeRunner` (Docker sandbox, Judge0 batch), async grading job, hidden cases never leave the server |
| AI calls block the request; no fallback when keys are missing   | Provider abstraction (any OpenAI-compatible endpoint) + deterministic offline provider; reports generated by background jobs; streaming questions over SSE |
| Report = one blob with `humanReviewRequired: true`              | Structured report: per-competency score, anchor level, evidence quotes linked to turns, confidence, "not assessed" state; separate integrity panel; recruiter decision with reason |
| No consent, no notices, no retention                            | Versioned AI-disclosure consent gate, proctoring telemetry with disclosure, retention purge job, candidate data deletion |
| Two tests                                                       | Unit + integration test suites against real Postgres, CI workflow                                  |
| No UI                                                           | Full React application for candidates and recruiters                                              |

## 3. Stack

- **Runtime**: Node.js 24 LTS (Node 20 is end-of-life), TypeScript 5.9, pnpm workspaces.
- **API**: Fastify 5, Zod 4 (`fastify-type-provider-zod`), `@fastify/swagger` (OpenAPI 3 at `/docs`),
  pino logging, `@fastify/rate-limit`, `@fastify/helmet`, `@fastify/cors`, `@fastify/cookie`,
  `@fastify/multipart`.
- **Database**: PostgreSQL 16 with Drizzle ORM + drizzle-kit migrations. `pg-boss` (Postgres-backed
  queue) for background jobs and cron, so no Redis is required.
- **AI**: OpenAI Node SDK pointed at any OpenAI-compatible base URL (OpenAI, Gemini compatible
  endpoint, DashScope/Qwen compatible mode, Groq, Ollama, vLLM). `MockAiProvider` when no key is
  configured so the whole product is demoable offline.
- **Voice**: browser Web Speech API by default (STT + TTS, zero cost); server endpoints
  `/ai/transcribe` and `/ai/speak` use provider audio models when configured.
- **Code execution**: `DockerRunner` (ephemeral containers, no network, CPU/memory/pids/time limits)
  for self-hosting, `Judge0Runner` (batch API) for managed hosting, `UnsafeLocalRunner` for
  development only.
- **Web**: Vite, React 19, React Router 7, TanStack Query 5, Tailwind CSS 4, Radix primitives,
  Monaco editor, zustand (auth/session state), react-hook-form + Zod.
- **Tests**: Vitest (API integration against Postgres, unit tests for scoring/state machine/runners),
  GitHub Actions CI.
- **Deploy**: multi-stage Dockerfiles for `api` and `web`, `docker-compose.yml` (postgres, api, web),
  migrations run on boot, health/readiness endpoints, Prometheus metrics.

## 5. Domain model

```
users ──< memberships >── organizations ──< org_invites
  │                              │
  ├──< refresh_sessions          ├──< jobs ──< question_bank
  ├──< password_resets           │        ├──< coding_problems (test cases as jsonb: input, expected, is_sample, weight)
  ├──< resumes                   │        └──< interview_invites ──> interviews
  └──< consents                  │
                                 └──< audit_logs
interviews ──< interview_turns        (question / answer pairs, per-turn evaluation)
           ──< transcript_events       (append-only: speaker, text, section, timestamps)
           ──< code_submissions        (problem, language, source, verdicts per case, score)
           ──< proctoring_events       (focus_lost, paste, fullscreen_exit, …)
           ──1 reports                 (per-competency scores + evidence + recommendation)
           ──1 decisions               (recruiter decision, reason, decided_by)
email_outbox                           (dev transport + delivery log)
```

### Interview state machine

```
invited ──(candidate accepts)──> ready ──(start, consent recorded)──> in_progress
in_progress ──(all sections done | candidate finishes)──> submitted ──(report job)──> completed
in_progress ──(deadline passed; sweep job)──> expired ──(report job on partial evidence)──> completed
invited/ready ──(recruiter cancels | invite expires)──> cancelled
```

Each interview snapshots the job's `interviewPlan` at invite time so later job edits do not
change a running interview. Sections are `{ type: 'conversation' | 'coding', durationMinutes,
questionCount?, problemIds? }`. The server computes `sectionDeadline` and `overallDeadline` on
section start; writes after a deadline are rejected with `410`.

### Rubric and scoring

A job has 2–8 competencies `{ key, label, description, weight, anchors? }` with weights summing
to 100. The report has, per competency: `score` (0–100 or `null` = not assessed), `level`
(1–5 anchor), `confidence` (0–1), `evidence[]` (quotes with `turnId`/`submissionId`). The
weighted score only counts assessed competencies and reports `coverage` (share of weight that
was assessed). Recommendation ∈ `strong_hire | hire | borderline | no_hire | insufficient_evidence`.
Coding correctness is computed deterministically from test results, not by the LLM.

## 6. API modules (all under `/api/v1`)

| Module        | Responsibilities                                                                              |
| ------------- | --------------------------------------------------------------------------------------------- |
| `auth`        | register (candidate / recruiter+org), login, refresh, logout, logout-all, forgot/reset password, verify email, sessions |
| `users`       | profile, avatar-less; candidate data export/deletion request                                 |
| `orgs`        | organization profile, members, invites, roles                                                 |
| `jobs`        | CRUD, publish/archive, competencies, interview plan, question bank, coding problems            |
| `invites`     | create/cancel interview invites, accept via token, resend                                      |
| `resumes`     | upload (PDF/DOCX), text extraction, async parse job, structured profile                        |
| `interviews`  | candidate: list, detail, consent, start, next question (SSE stream), answer, transcript, section advance, finish; recruiter: list/filter, detail, transcript, decision |
| `coding`      | problems for an interview section (sample cases only), run (sample), submit (async grade), submission status, languages |
| `proctoring`  | batched client telemetry events                                                               |
| `reports`     | report fetch, regenerate, recruiter rankings per job, CSV export                               |
| `ai`          | provider status, transcribe, speak (TTS)                                                      |
| `admin`       | platform stats (superadmin), mail outbox (development only)                                   |
| `health`      | `/health/live`, `/health/ready`, `/metrics`                                                   |

Conventions: JSON envelopes are not used; success returns the resource, errors return
`{ error: { code, message, details? } }` with proper HTTP status. Cursor/offset pagination
`{ items, total, page, pageSize }`. Every request carries `x-request-id`.

## 7. Security model

- Passwords: bcrypt cost 12, 10–128 chars, breached-pattern checks; 10 failed logins ⇒ 15 min lockout.
- Access token: 15 min JWT (HS256, `jose`), carried in memory on the client, `Authorization: Bearer`.
- Refresh token: 32-byte random, SHA-256 hash stored in `refresh_sessions`, httpOnly `SameSite=Lax`
  cookie scoped to `/api/v1/auth`, rotated on every use, family revoked on reuse detection.
- Authorization: route-level role guard + resource-level org membership checks in services.
- Hidden test case inputs/outputs never serialized to candidates; recruiter only after auth.
- Rate limits: global 300/min per IP, auth endpoints 10/min, AI endpoints per user.
- Uploads: MIME + extension + magic-byte check, 5 MB cap, stored outside web root or S3.
- Prompt-injection hardening: resume/answers are delimited as untrusted data; model output is
  schema-validated; names and contact details are redacted before scoring prompts.
- Audit log for every recruiter read of a report/transcript and every decision/override.

## 8. Compliance-driven features

- Versioned AI disclosure text; consent stored with text hash, timestamp, IP, user agent.
- Proctoring telemetry is disclosed in the same consent and is surfaced in a separate
  integrity panel, never mixed into the score.
- Human decision required: recruiters click `hire/advance/reject/hold` with a reason; the
  system never emits an adverse decision by itself.
- Candidate can request deletion; a job purges files, transcripts, and reports and keeps an
  anonymized tombstone. Retention purge job (default 365 days, configurable).
- Export: per-job CSV of scores for bias audits; audit log export.

## 9. Background jobs (pg-boss)

| Queue                | Trigger                       | Work                                               |
| -------------------- | ----------------------------- | -------------------------------------------------- |
| `resume.parse`       | after upload                  | extract structured profile via AI provider         |
| `submission.grade`   | on submit                     | run all cases through `CodeRunner`, store verdicts |
| `report.generate`    | on finish/expiry              | build evidence pack, call AI, validate, store      |
| `email.send`         | invites, resets, notifications| nodemailer (SMTP) or dev outbox                    |
| `interview.expire`   | cron `* * * * *`              | mark overdue in-progress interviews expired, enqueue reports |
| `retention.purge`    | cron `0 3 * * *`              | delete data past retention                         |

## 10. Frontend information architecture

- **Public**: landing, login, register (candidate), recruiter sign-up (creates org), forgot/reset
  password, accept invite (`/invite/:token`).
- **Candidate**: dashboard (upcoming/completed interviews, resume status), profile & resume,
  interview lobby (instructions, device check, consent), interview room (conversation), coding
  room (Monaco IDE), completion page.
- **Recruiter**: dashboard (pipeline stats), jobs list, job detail (overview, rubric, interview plan,
  question bank, coding problems, candidates & invites, rankings), new/edit job, interview detail
  (summary, Q&A transcript with per-turn evaluation, code submissions with test matrix, report,
  integrity panel, decision), organization settings (members, invites), AI/integration status.
- **Development only**: mail outbox viewer to click invite/reset links without SMTP.

Design language: neutral slate surfaces, teal accent, generous whitespace, 8-pt spacing scale,
Inter typeface, dark mode, keyboard-navigable, WCAG AA contrast, visible focus rings.

## 11. How it was delivered

The rewrite was built in the order below, each step landing with its tests before the next began.
All of it is in place.

1. Monorepo scaffold, shared contracts package, API skeleton with health, config, logging, DB, migrations.
2. Auth, users, organizations, invites, email, audit log; integration tests.
3. Jobs, competencies, question bank, coding problems, interview plan.
4. Resumes (upload, extraction, async parse), AI provider layer with the offline provider.
5. Interviews: invites, consent, state machine, conversation section (SSE questions, answers,
   evaluations), timing, proctoring events.
6. Coding: runner abstraction (Docker, Judge0, local), run/submit, grading job.
7. Reports: evidence pack, scoring, recommendation, recruiter decision, rankings, export.
8. Web app: UI kit, auth flows, candidate flows, interview room, coding room, recruiter flows.
9. Hardening: rate limits, retention, deletion, metrics, Dockerfiles, compose, CI, docs.

## 12. Trade-offs worth knowing

- **PostgreSQL over MongoDB.** The domain is relational (organizations, jobs, interviews, turns,
  submissions, reports) and the recruiter views are joins and aggregates. Moving to Postgres also
  gave us transactional invariants and pg-boss, which removed the need for Redis.
- **Server-sent events over WebSockets.** The only truly real-time element is the interviewer's
  streamed question. SSE works through every proxy and load balancer without special handling and
  needs no connection state on the server. Deadlines are enforced on each write instead of being
  pushed, which is also more robust.
- **One OpenAI-compatible adapter instead of per-vendor SDKs.** Every mainstream provider speaks
  the chat-completions protocol now; the adapter is small, testable, and vendor changes are a
  configuration edit.
- **Shipping an offline AI provider.** It makes development, demos and CI independent of
  credentials and quota, and it forced the report pipeline to validate model output strictly, since
  the offline provider exercises the same code path.
- **Docker sandbox in addition to Judge0.** Judge0 CE cannot run on hosts with cgroup v2, which is
  every modern Linux. A first-party sandbox keeps the product self-hostable on one machine.
